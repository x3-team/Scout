на ref `969ed414a761b701f21559ac68edcf9b7ac27b6b`.
Проверяемый canonical ref: `a880fac2d17a3eae541945640ee5a1d72d6cf202`, draft.2.

Первые два примера R2 демонстрируют недостаточность draft.2 относительно уже
предложенной SkillForge модели сегментов; они не объявляются допустимыми или
недопустимыми по ещё не согласованному API. Первый не доказывает реальное
воспроизведение старого результата: он доказывает, что формат не позволяет
отличить такой replay от свежего результата другой цели.

Дополнительный структурный вывод R2: session_id детерминирован, epoch отсутствует
во всех четырёх сообщениях. Две живые попытки с тем же session/step неразличимы
по проводу. Нужен отдельный уникальный epoch на попытку, не зависящий от seed;
restart worker завершает старую попытку, поздние ответы отвергаются по активному
состоянию. Один общий clock/budget сохраняется при A/B/C/HOME и при инспекции.

SCOUT-C1 — новое локальное замечание повторного ревью, не переименование R3
SkillForge. Прежняя R3 проверяла вывод из фактического sensor/guard/stop state;
здесь обратная проверка самой заявленной пары status/reason. Нужна, например,
однозначная таблица completed→GOAL_REACHED, blocked→PATH_BLOCKED,
timeout→MISSION_TIMEOUT; fault→согласованные коды неисправностей. Это проект
таблицы для следующей ревизии, не уже существующая wire-норма.

## Команда и исходный отчёт

```powershell
python scripts/review_integration_contract.py --output runs/contract-second-pass.json
```

[Исходный JSON](evidence/contract-second-pass.json) содержит шесть диагностических
проб с точными изменениями, observed/required и сообщениями отказа. Положительный
контроль подтверждает допустимость команды шага 3599 после R1. Проверено Linux /
CPython 3.12.14. Код 0 здесь означает «известные пробелы воспроизведены»;
`decision=request-revision` и `contract_accepted=false` остаются явными.
При исправлении семантики скрипт потребует пересмотра baseline, а не молча
объявит контракт принятым. Это не runtime validator и не выполненная интеграция.
